## Truthful execution concurrency

The previous plan divided threads across requested workers even though the persistent native implementation shares one synchronous model process. Short/unchunked audio could also divide threads among workers that never ran. Plans now cap effective execution to one for those paths and by the available chunk count for CLI-only dispatch. Requested workers, effective limits and reasons remain visible in resource diagnostics; saved options/checkpoints are preserved. The single worker receives the full permitted thread budget. RAM estimates, reserve, defaults and cloud behavior were not relaxed to make tests pass.

Planner regressions first failed with 4 workers instead of 1 for the persistent path and 5 instead of 2 for two available CLI chunks. After correction, the complete desktop/pipeline file passed 24/24, zero failed/skipped, in 2.05 s. This corrects allocation/reporting; it does not establish optimal CPU/thread settings or a throughput improvement.
